PROVEN FAILURE AND ALTERNATIVE
07-scratch-identity-verified.json demonstrates 25,300 overlapping newly generated
IDs after alternating inserts into a source and its clone. The first few values
looked disjoint; only testing beyond allocation blocks exposed the collisions.
Do not use a clone plus an INGESTION_ID anti-join while both generators run.

08-scratch-disjoint-ids.json verifies a separate destination range starting at
1,000,000,000,000: 20,003 distinct rows after historical copy plus old/new writes
and catch-up, zero payload mismatches, and 20,004 distinct rows after rollback
reconciliation and one new source write. The same approach is used for OPTION_ID.
Existing IDs are preserved. New IDs remain within exact JavaScript integer range.
Runtime SQL guards reject source IDs outside the reserved old range and reject
same-ID/different-payload collisions. Never interpret a NOORDER ID as a watermark.

A rehearsal also exposed a GET_DDL replay incompatibility: the legacy POLL_ID
column is VARCHAR(16777216), while a bare VARCHAR cast now resolves to a larger
width. 10-prepare.sql explicitly preserves the old virtual-column expression width.

CUTOVER ORDER — NOT EXECUTED
1. Resolve the Braze CDI inventory and the external-reader handoff. The drafted
   compatibility views cover old-name SELECT consumers; if those are rejected,
   arrange every external consumer's repoint before switching production.
2. Verify the source definitions/grants and production git head have not changed.
   Capture each workflow's current activation state. Pause/drain catalog sync,
   taxonomy, text classification, reporting and MCP writes; retain live ingest.
   Also stop any manual enrichment/classifier scripts for the cutover window.
3. Run 10-prepare.sql in one session with stop-on-error. Verify every source
   snapshot/destination count and hash pair matches and all views compile.
4. Deploy the prepared six-workflow change together via the synced production
   branch. Verify deployed SQL/configuration as well as custom-step code hashes.
   Wait for propagation and old ingest runs to drain; no idle interval alone
   proves drain. Use workflow execution status and recent Snowflake query history.
5. Run 20-catchup.sql until there are no missing old-side rows, then 30-verify.sql.
   Keep all dimension writers paused until these checks pass.
6. After confirming every writer uses the destination, apply 40-compatibility.sql
   if selected. There is a short per-object gap between RENAME and CREATE VIEW;
   readers may need to retry during that handoff. Do not claim an atomic switch.
   Repoint known readers directly where their owners can deploy the change.
7. Restore the previously captured workflow states. Verify an authorized test
   response through the actual public endpoint, its persisted new-schema record,
   tally behavior, a report, classification and downstream Harbor reads. Confirm
   there are no successful writes to old archived tables. Keep old archives.
8. Land the Python/Harbor configuration changes through their repo review flows;
   do not allow a future deploy to restore the old literal references.

ROLLBACK
Freeze and drain both sides' writers. If compatibility was fully installed, run
50-restore-source-names.sql. If it failed partway, inspect each object's kind and
restore only completed renames; never blindly run the whole file. Then run
60-rollback-reconcile.sql with stop-on-error and explicit ROLLBACK on any error.
Check complete parity before restoring the prior workflow commit and activation
states. Keep the destination intact for investigation. Do not drop either schema.
